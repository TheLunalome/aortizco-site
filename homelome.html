04 · storage

Capacity is only useful when recovery has a story too.

Capacity, data placement, backup copies, and recovery evidence are distinct concerns. A storage path alone does not demonstrate recoverability.

Separate data roles

Capacityworking storage
Copybackup destination
Restorerecovery evidence

Each role needs its own coverage and restore evidence. This public guide does not describe particular storage systems or their current state.

Recovery questions

  • Which data is included in a copy?
  • Is the copy independent of the primary system?
  • Has recovery been tested?

05 · access

Useful access needs boundaries.

Remote access should be narrower than curiosity. These are general design principles, not a report of current configuration.

01

Identity at the edge

An identity-aware boundary can check a request before a protected service is reached.

02

Limit inbound exposure

Prefer controlled outbound connections over exposing management interfaces directly.

03

Separate service permissions

One portal sign-in should not replace each service's own authentication and permissions.

04

Read first, write deliberately

Read-only inspection can be the default. Changes need their own scoped authorization.

06 · evidence

Separate design from observation.

A public architecture guide should distinguish a documented design, a dated observation, and an unresolved assumption. This guide publishes no live system state.

Observation is not health

A configuration or inventory record describes what is declared or present. It does not prove the health of every application.

Recovery requires evidence

A configured backup is not a successful restore. Describe the evidence and its limits before claiming recoverability.

07 · field notes

The most important upgrades are usually unglamorous.

A useful architecture guide says what it knows, names what it does not, and keeps the recovery path clear.

Monitoring beats vibes. A service that looks fine on a dashboard can still be broken.

Operating principle
Why publish a public-safe architecture page?

Architecture is more useful when it explains decisions. This guide can show the boundaries, roles, and tradeoffs without making the home environment easier to target.

What counts as evidence?

Name the source and observation date. Keep configuration, observed behavior, and unknowns separate.

What happens after an outage?

The goal is a small evidence trail: symptom, actual cause, alert behavior, repair, and the guardrail added afterward. That is more useful than a perfect-looking dashboard.
